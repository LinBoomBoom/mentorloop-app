# 任务卡 SOP（G1 契约门 · 入口）

生成日期：2026-09-24
归属：SOP 系统 L3 执行层 · 生命周期阶段 ① 定义
上游：[README.md](./README.md) §2–3；下游：`quality-gate-sop.md`（G2）

---

## 1. 目的与适用

任何**新任务、缺口、功能请求**在动代码之前，必须先形成一张任务卡；任务卡通过 G1 契约门后才进入「② 构建」。

- **适用**：新功能、闭环缺口、领域改造、内容补齐、原生插件、支付/合规项。
- **不适用**：已有任务卡的日常修复；纯文档错别字等零风险改动（可免卡，但需在 commit 说明原因）。

---

## 2. 八要素（缺项不得进入迭代）

| #   | 要素         | 要求                                            |
| --- | ------------ | ----------------------------------------------- |
| 1   | **目标**     | 一句话说明要解决什么、为什么现在做              |
| 2   | **范围**     | 明确「做什么」与**明确不做什么**（防范围蔓延）  |
| 3   | **依赖**     | 前置任务、外部环境（HBuilderX/密钥/资质）、契约 |
| 4   | **验收标准** | **可判定**的通过条件（能写测试或能逐项勾选）    |
| 5   | **风险**     | 已知风险 + 对策                                 |
| 6   | **产物路径** | 将新增/修改的文件路径                           |
| 7   | **角色**     | 参与角色 + 主责，使用 `roles-sop.md` 代号       |
| 8   | **负责人**   | 最终负责人（角色 + 执行 Agent）                 |

> 第 7 项「角色」把任务绑定到 `roles-sop.md` 的角色目录，确保门禁责任落到具体角色（如 FE / UX / FA / QA）。

## 4. G1 契约门检查清单

进入「② 构建」前逐项确认：

- [ ] 八要素**全部**填写，无空缺。
- [ ] 「范围」明确写了**不做什么**。
- [ ] 「验收标准」可判定（能写成测试或可勾选），不是「体验良好」这类主观描述。
- [ ] 「角色」使用 `roles-sop.md` 代号，主责与任务类型匹配（如客户端改动主责 FE）。
- [ ] 若涉及 `types/` 或 `api/` 变更 → 已产出**契约冻结单**并完成客户端 + 后端双签。
- [ ] 「产物路径」覆盖全部预期改动文件。

**失败动作**：任一项不通过 → 退回「① 定义」补齐，不得开工。

## 5. 示例（节选）

```markdown
# 任务卡：报告薄弱项一键进入定向训练

- 日期：2026-09-24
- 关联：闭环缺口 #1

## 1. 目标

让报告页的薄弱项点进去后，训练房间出的是该维度题，训练结果在成长页可追溯。

## 2. 范围

- 做：报告页带参跳转；选题器按维度过滤；训练记录落库；成长页合并展示。
- 不做：服务端同步训练记录（跨设备同步归 P1 后续）。

## 3. 依赖

- 前置：无（纯前端）
- 外部环境：无
- 契约：不改 types/ 与 api/，无需契约冻结

## 4. 验收标准

- [ ] 报告薄弱项点击后进入训练，首题属于该维度
- [ ] 训练完成后成长页可见该条记录，并可与面试报告对照

## 7. 角色

- 主责：FE
- 配合：UX / QA

## 8. 负责人

客户端工程师（客户端 Agent）
```
