# 免费预览恒为 0 条：DeepSeek 思考模式吃满 max_tokens

## 问题现象

真机走查中上传 PDF 走免费预览，`POST /resume/parse` 返回 200、`mode=preview`、技术栈识别正确（Java / Spring / Spring Boot / MySQL / Redis），但 **`previewIssues=[]`**，客户端因此显示「本次未发现明显问题」，而简历实际存在明显量化缺失。

## 问题分析

本地用同一 prompt 复现（`deepseek-v4-flash`）：

| 配置            | finish_reason | content 长度 | completion_tokens | reasoning_tokens |
| --------------- | ------------- | ------------ | ----------------- | ---------------- |
| max_tokens=700  | `length`      | **0**        | 700               | **700**          |
| max_tokens=2000 | `stop`        | 893          | 1250              | 855              |

结论：DeepSeek v4 默认开启思考模式，`reasoning_content` 与 `content` 共享 `max_tokens`。预览的 700 tokens 被推理全部占满，正文为空 → `chatComplete` 返回 `null` → 预览回退结构预览（`previewIssues=[]`）。

同类风险：完整评审（2000）、报告增强（默认 900）在长输入下也会被推理挤掉正文，只是概率不同。

## 处理措施

1. `server/src/llm/client.ts` 新增 `thinking` 选项，**默认 `disabled`**，且只对模型名含 `deepseek` 的请求注入（避免第三方兼容接口 400）。
2. 新增 `server/src/llm/client.spec.ts` 5 例锁定：默认关闭、显式开启透传、非 DeepSeek 不注入、HTTP 失败返回 null、content 为空返回 null。
3. 附带收益：关闭思考后同一请求 completion_tokens 由 700（全推理）降到 417，延迟由秒级降到百毫秒级。

## 后续建议

- 报告增强（`llm/report-enhancer.ts`）与完整评审同样走 `chatComplete`，已随本次默认值一并修复；若后续引入需要推理的场景，再显式传 `thinking: 'enabled'` 并同步放大 `maxTokens`。
- 任何新增 LLM 调用点都要先确认「思考模式是否开启」与 `maxTokens` 是否够容纳「推理 + 正文」。
