# 损坏 JSON 请求体可击穿进程（自定义解析器同步 throw 未捕获）

## 问题现象

- 触发操作：本地服务端 `pnpm dev`（tsx watch，127.0.0.1:8787）收到一条字面反斜杠转义的请求体 `{\"events\":[\"2026-10-11T13:50:49.7944858+08:00|app_launch|{}\"]}`（POST /track/batch，content-type: application/json）。
- 预期 vs 实际：预期返回统一失败响应（fail 包络）；实际 `JSON.parse` 抛出 SyntaxError，穿透 Fastify 解析管线以 uncaughtException 杀死整个进程，日志尾部直接输出 Node 版本号（进程退出）。
- 报错信息：`SyntaxError: Expected property name or '}' in JSON at position 1`，栈顶 `app.ts:46` 自定义 content-type parser。

## 问题分析

- `server/src/app.ts` 为保留原始字节（微信支付回调验签）覆盖了默认 JSON 解析器，`done(null, JSON.parse(text))` 在解析失败时同步 throw。
- Fastify 5 的 `content-type-parser.js` 调用解析函数处没有 try/catch 包裹——解析错误约定必须通过 `done(err)` 上报，同步 throw 会沿 `IncomingMessage.onEnd` 逃逸成 uncaughtException。
- 该缺陷同样存在于云端镜像（同一份代码）：任何客户端 bug / 扫描器探测的畸形请求体都可能导致云托管容器崩溃重启。
- 触发载荷来源推断：崩溃时间 13:50:49 与当日排查 /track/batch 的时间线吻合，载荷形态为 Windows cmd 风格 `\"` 转义，判定为诊断期手工 curl 请求（客户端 client.uts 全程传对象、单次序列化，无双重编码路径）。

## 处理措施

- 解析器改为 try/catch：解析失败构造 `statusCode=400` 的 Error 走 `done(err)`，由 `setErrorHandler` 统一映射为 `fail(400, '请求体不是合法 JSON')`；空请求体保持原 `{}` 行为。
- 新增 `server/src/app.spec.ts` 回归测试：崩溃同款载荷 → 断言统一 400 包络 + 后续 /healthz 存活；空请求体 → 路由校验 400。
- 顺带修复 `server/package.json` lint 脚本引用不存在的 `tests` 目录（改为 `eslint src --ext .ts`）。
- 门禁：server lint/tsc/vitest 60/60/prettier 全绿。

## 后续建议

- 服务端凡自定义 Fastify 插件/parser 回调，错误一律走 `done(err)` / `next(err)`，禁止依赖同步 throw；可在 code review 清单中加一条。
- 云端可观测性：容器异常退出目前无告警，后续接云托管告警通知（另立卡）。
