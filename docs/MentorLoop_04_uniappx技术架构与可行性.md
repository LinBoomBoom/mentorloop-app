# MentorLoop AI 面试产品：uni-app x 技术架构与可行性

## 1. 技术结论

采用 **uni-app x 作为小程序、Android 与 iOS 的主客户端框架** 是可行且合适的。目标不是“完全不写原生代码”，而是让 70%–80% 的页面、业务和状态逻辑跨端复用；将 20%–30% 的实时音频、数字人渲染、设备权限和异常恢复封装为 UTS 原生插件。

uni-app x 适合普通业务页面、报告、题库、简历优化和状态化面试房间。实时语音和数字人场景需要专门的性能设计与真机验收，不能仅以模拟器流畅度作为依据。

## 2. 总体架构

```text
客户端（uni-app x）
├─ uvue 页面与通用组件
├─ 会话状态机与本地草稿
├─ API / WebSocket 客户端
└─ UTS 插件
   ├─ interviewer-audio：录音、降噪、音频焦点、中断恢复
   ├─ interviewer-realtime：流式 ASR/TTS、断线重连、缓冲
   ├─ interviewer-avatar：口型、动作、缓存、渲染桥接
   └─ interviewer-device：权限、网络、前后台、诊断

服务端
├─ API 网关与身份认证
├─ 面试会话编排服务
├─ 岗位画像、题目与追问服务
├─ 评分与报告服务
├─ 简历解析与优化服务
├─ 内容运营后台与审核服务
└─ 支付、消息、埋点与风控服务

数据层
├─ 关系数据库：用户、题库、会话、评分、订单
├─ Redis：会话、限流、任务状态、缓存
├─ 对象存储：简历、录音、报告导出文件
└─ 分析仓库：埋点、漏斗、模型评测、运营数据
```

## 3. 面试状态机

```text
CREATED
→ DEVICE_CHECK
→ READY
→ ASKING
→ LISTENING
→ TRANSCRIBING
→ FOLLOW_UP_DECISION
→ NEXT_QUESTION 或 WRAP_UP
→ REPORT_GENERATING
→ COMPLETED
```

- 所有关键事件需带会话 ID、题目 ID、事件序号与幂等键。
- 客户端保存转写和作答草稿；网络恢复后按序补传。
- 录音异常、切后台、来电、权限收回均进入可恢复状态，不允许静默丢失答案。

## 4. 性能规则

1. 音频帧、口型和波形不进入高频响应式状态；在绘制层或原生层处理。
2. UI 每秒只同步 10–15 次摘要状态，不随每个音频包更新。
3. 面试房间仅维护一个活跃数字人实例；退出立即释放音频与纹理资源。
4. 题库与报告列表使用虚拟滚动或分页；避免过深节点和大面积阴影动画。
5. 数字人按角色、场景、服饰分包，首屏只下载当前面试所需资源。
6. 设备端不做大模型推理；模型、评分、TTS 合成优先运行于服务端。

## 5. 数据、安全与隐私

- 简历、录音、转写与报告均为高敏感数据；按用途、期限和权限分级存储。
- 默认不将用户原始录音用于训练模型；若需要，必须单独、可撤回地取得授权。
- 传输使用 TLS；敏感字段加密；后台访问采用最小权限与审计日志。
- 提供录音提示、隐私政策、数据导出和删除入口。
- 对提示词注入、违规生成、刷接口、账号盗用、恶意上传实行服务端防护。

## 6. 测试与发布门槛

### 两周技术预研

- 同一 uni-app x 页面成功发布到微信小程序、Android 和 iOS。
- 验证录音、流式转写、TTS 播放、音频打断和弱网重连。
- 验证一个 2.5D 角色口型同步、资源缓存和 20 分钟持续运行。
- 验证前后台切换、来电、蓝牙耳机、权限拒绝与恢复。

### 正式发布验收

- 主流 iPhone、中低端 Android、微信环境全量真机覆盖。
- 20 分钟模拟面试无崩溃、无明显内存持续增长、无答案丢失。
- 核心接口具备限流、熔断、重试、监控、报警和降级策略。
- 关键模型输出经人工评测集验收：题目相关性、追问质量、评分一致性、报告可执行性和安全性。
